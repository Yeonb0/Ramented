# 라멘타쿠 v2.0 — Phase 계획

## 이 문서의 역할

- v2.0 구현을 **Phase (수직 슬라이스) 7개**로 나눈다. Phase 하나는 앱에서 직접 눌러 볼 수 있는 기능 한 덩어리다
- Phase 안은 🎨 디자인 → ⚙️ 백엔드 → 📱 프론트 순서의 트랙으로 나눈다 (관리자님 2026-11-13, 선택지 A)
- **Phase마다 다른 세션에서 진행한다.** 각 세션은 `phases/PHASE{N}_CONTEXT.md` 하나와 이 문서의 "공통 규칙"만 읽고 시작할 수 있어야 한다
- 근거 문서 : `frame.md` (accepted) → `shaping.md` (selected) → `breadboard.md` (selected-design, 2026-11-13 수락) → `seed-survey.md`, `seed-attributes.md`

## Phase 한눈에 보기

| Phase | 이름 | 요구 | breadboard 흐름 | 선행 Phase | 가장 큰 불확실성 |
|---|---|---|---|---|---|
| 1 | 지도에 30곳이 보인다 | R7 | T1 | — | 공공데이터 좌표가 실제로 있는지, 가게 이름 매칭 |
| 2 | 가게와 메뉴를 살펴본다 | R1 · R3 · R4 | T4 · T5 | 1 | 메뉴 속성 상태 · 근거를 응답에 담는 모양 |
| 3 | 필터로 거른다 | R0 | T2 · T3 | 2 | 마커 세 모양을 WebView 안에서 바꾸는 방식 |
| 4 | 다녀온 한 그릇을 기록한다 | R5 · R8 | T6 ~ T9 · T14 ~ T16 | 3 | 속성 확정 규칙 (B5 · B9) 을 빠짐없이 테스트하기 |
| 5 | 지인 베타 시작 | (배포) | — | 4 | 서버 호스팅 선택, Play 비공개 테스트 등록 |
| 6 | 휴무 · 이벤트 제보 | R2 · R3 | T10 ~ T13 | 5 (베타 중 업데이트) | 영업 상태 계산에 제보 · 엇갈림을 합치기 |
| 7 | 정식 출시 | (배포) | T2b | 5 + 14일, 6 | 14일 연속 테스터 12명 유지 |

순서 이유 :

- **Phase 1이 맨 앞** : 좌표 출처 (공공데이터) 가 막히면 지도 자체가 안 된다. 가장 큰 불확실성을 먼저 푼다
- **필터 (3) 가 기록 (4) 보다 앞** : 필터는 시드 값만으로 동작을 확인할 수 있고, 기록이 들어오면 같은 필터에서 결과가 바뀌는 것을 바로 볼 수 있다
- **지인 베타 (5) 가 제보 (6) 보다 앞** : 해산물 제외 필터를 채우는 것은 기록 · 태깅 (4) 이다 (breadboard B1). 베타를 빨리 시작해야 Play 14일 조건이 일찍 돌아간다. 제보는 베타 중 업데이트로 넣는다
- R6 (등급 · 랭킹) 은 v2.0 cut이라 Phase가 없다

## Phase별 요약

### Phase 1 — 지도에 30곳이 보인다

- 목표 : 앱 첫 화면에 마포구 30곳이 보이고, 마커를 누르면 가게 이름과 정기 영업시간 기준 영업 상태가 보인다
- 🎨 기본 마커, 미리보기 시트
- ⚙️ Flyway 도입, v2 스키마 (가게 · 메뉴 · 라멘 종류), 시드 30곳 · 94줄, 공공데이터 좌표, 지도 API, 정기 영업시간 기준 영업 상태
- 📱 지도 화면 (로딩 · 오류), 기본 마커, 미리보기 시트, v1 기술 부채 정리
- 완료 기준 : 30개 마커가 보이고, 시트에 "영업 중 · 정기 영업시간 기준" 같은 문구가 나온다

### Phase 2 — 가게와 메뉴를 살펴본다

- 목표 : 가게 상세와 메뉴 상세에서 한 그릇의 속성과 근거를 볼 수 있다
- 🎨 가게 상세, 메뉴 상세, 속성 배지
- ⚙️ 가게 상세 · 메뉴 상세 API, 속성 상태 계산 (시드 단계), 별점 집계 (빈 상태)
- 📱 가게 상세 · 메뉴 상세 화면
- 완료 기준 : 메뉴마다 종류 · 형태 · 해산물 · 국물과 근거가 보이고, 별점 자리에 "아직 평가 없음"이 나온다

### Phase 3 — 필터로 거른다

- 목표 : 해산물 제외 · 국물 칩으로 가게를 거른다
- 🎨 필터 칩, 마커 "통과 n개" · 흐림, 0곳 안내
- ⚙️ 필터 판정
- 📱 필터 바, 마커 세 모양, 0곳 안내, 가게 상세에서 통과 메뉴 위로
- 완료 기준 : 청탕 칩을 켜면 청탕 메뉴가 있는 4곳만 배지로 남고, 해산물 제외를 켜면 0곳 안내가 나온다

### Phase 4 — 다녀온 한 그릇을 기록한다

- 목표 : 회원이 메뉴를 기록 · 태깅하고, 태깅이 메뉴 속성을 바꾼다
- 🎨 로그인, 기록 작성, 내 기록, 프로필
- ⚙️ 회원 · JWT, 기록 저장, 태깅, 속성 확정 규칙 전체, 회원별 최근 별점
- 📱 로그인 흐름, 기록 작성, 내 기록 탭, 프로필 탭
- 완료 기준 : 두 계정이 "안 들어있음"을 태깅하면 그 메뉴가 미포함 확정이 되고, 해산물 제외 필터에서 가게가 나타난다

### Phase 5 — 지인 베타 시작

- 목표 : 지인들이 설치해서 실제 서버에 기록을 남긴다
- ⚙️ 서버 호스팅, 운영 DB 시드, 개인정보 처리방침 URL
- 📱 Expo 빌드 · 테스트 배포, Play 비공개 테스트 등록
- 완료 기준 : 테스터 12명 이상이 비공개 테스트에 참여해 14일 카운트가 시작되고, 첫 기록이 운영 서버에 들어온다

### Phase 6 — 휴무 · 이벤트 제보

- 목표 : 인스타를 쓰지 않아도 오늘 휴무와 이벤트를 앱에서 안다
- 🎨 제보 모달, 영업 상태 문구 변형, 이벤트 한 줄
- ⚙️ 제보 저장 · 만료, 영업 상태 계산에 제보 반영
- 📱 제보 화면, 인스타 · 카카오맵 링크
- 완료 기준 : 휴무를 제보하면 가게 상세가 "휴무 · 제보 (인스타에서 봄) · 방금"으로 바뀌고, 24시간 뒤 정기 영업시간 기준으로 돌아온다

### Phase 7 — 정식 출시

- 목표 : Google Play 프로덕션 출시를 신청한다
- 완료 기준 : 14일 연속 조건을 채운 뒤 프로덕션 출시 신청을 제출한다

## 공통 규칙 (모든 Phase 세션)

### 세션 시작

1. 저장소 main을 최신으로 받는다
2. `docs/planning/phases.md` 의 이 절과 `docs/planning/phases/PHASE{N}_CONTEXT.md` 를 읽는다
3. 앞 Phase의 `docs/planning/phases/PHASE{N-1}_HANDOFF.md` 가 있으면 읽는다
4. 더 필요할 때만 packet이 가리키는 `breadboard.md` 의 해당 ID를 찾아 읽는다. 기획 문서 전체를 읽을 필요는 없다

### 근거의 우선순위

1. 관리자님의 명시적 결정 (대화에서)
2. `breadboard.md` (selected-design) · `shaping.md` (selected) · `frame.md` (accepted)
3. 이 문서와 Phase packet
4. `seed-survey.md` · `seed-attributes.md` (시드 데이터의 근거)
5. v1 문서 (README 로드맵, `docs/ramen-classification.md`, `docs/api-contract.md`, `docs/ramentaku_screendesign.md`) — 참고만 하고, 위와 충돌하면 위가 이긴다

### 설계 원칙 (프로젝트 지침과 같음)

- 국물 속성과 별점은 메뉴 (`ShopRamen`) 단위
- 별점 옆에는 항상 메뉴명
- 파생 값 (영업 상태, 속성 상태, 별점, 필터 판정) 은 서버가 계산한다. 클라이언트는 재계산하지 않는다. API 응답은 화면이 필요로 하는 것에서 역산한다
- 앱 코드는 라멘 이름 문자열을 파싱해 속성 · 색을 고르지 않는다 (시드 근거로 이름을 쓰는 것은 운영자 작업이라 별개)
- 화면마다 로딩 / 에러 / 빈 상태를 모두 구현한다
- 그림자 · 그라디언트 · 이모지 아이콘 · 토큰 밖의 색 금지. 화면 코드에 헥사값 · 픽셀 상수를 쓰지 않는다 (`app/src/theme` 이 단일 출처)
- 지도 마커는 WebView 안에서 SVG 문자열로 그린다 (`buildMarkerSvg`)

### Phase 안의 순서

🎨 디자인 (시안 · 토큰 확인) → ⚙️ DB · 엔티티 → API + 테스트 → 📱 프론트 타입 → API 호출 함수 → 훅 → 화면 → 상태 연동

- API 계약을 바꾸면 같은 커밋 단위 안에서 백엔드와 프론트를 함께 맞춘다
- 새 API를 만들기 전에 `docs/api-contract-v2.md` 에 해당 엔드포인트를 먼저 적고 관리자님 확인을 받는다 (필드 이름 · nullable · enum 값)
- 시안이 없는 화면은 토큰 + 공통 프리미티브 조합으로만 만든다

### 커밋 · PR

- 브랜치 : `feature/phase{N}-{기능-요약}`
- 커밋 : `<type>(<scope>): <설명>` + 본문 (무엇을 왜)
- PR 제목 : `[Phase N] <기능 요약>`, 본문 : 무엇을 / 왜 / 어떻게 / 체크리스트 / 테스트
- 커밋할 단위가 끝나면 "여기서 커밋할 차례입니다"라고 알리고, 브랜치 · 커밋 · push · PR까지 한 뒤 멈춰서 머지를 기다린다
- 관리자님이 "머지했어"라고 하면 main을 다시 받아 이어간다

### 기술 메모

- 프론트 : React Native + Expo SDK 54 (managed) + expo-router + TypeScript, TanStack Query, react-native-svg, 카카오맵 JavaScript SDK via react-native-webview
- 백엔드 : Java 25 + Spring Boot 4.1, Spring Data JPA, Spring Security + JWT, PostgreSQL
- **Spring Boot 4 테스트 슬라이스 패키지가 바뀌었다** (README 참조) : `@DataJpaTest` → `org.springframework.boot.data.jpa.test.autoconfigure`, `TestEntityManager` → `org.springframework.boot.jpa.test.autoconfigure`, `@WebMvcTest` → `org.springframework.boot.webmvc.test.autoconfigure`
- 스크립트는 Windows에서도 돌아가야 한다 (POSIX 셸보다 Node.js)

### Phase를 끝낼 때

1. 완료 기준을 실제로 확인한다 (테스트 실행, 앱에서 흐름 확인)
2. `docs/planning/phases/PHASE{N}_HANDOFF.md` 를 쓴다 : 한 것, 바뀐 계약, 남은 것, 다음 Phase가 알아야 할 것, 근거와 다르게 간 결정
3. "Phase N이 끝난 것 같습니다"라고 알리고 `/devlog:publish phase-N` 실행을 제안한다 (직접 실행하지 않음)
4. 세션을 마칠 때 이번 세션의 결정과 이유를 `/devlog:note` 로 남길지 묻는다

### 기획으로 돌아가야 할 때 (구현을 멈추고 관리자님께 묻는다)

- 필요한 동작이 `breadboard.md` 에 없다
- 구현하려면 Phase 범위를 넘거나 v2.0 cut (등급 · 랭킹, 인증샷, 사용자 가게 등록, 이벤트 상세, 인스타 게시물 표시, 사장님 참여) 을 건드려야 한다
- 필드 · enum · nullable · 오류 처리 · 기대 결과가 정해져 있지 않고, 정하는 것이 화면 동작을 바꾼다
- 구현 중 알게 된 사실이 기획 가정을 깬다 (예 : 공공데이터에 좌표가 없다)
- 한 Phase가 두 달 넘게 끝나지 않는다 (shaping의 재검토 조건)
